    跨仓库综合观察

    1. **"logits 提取无壁垒"被最直接证实**：SemIf（04B 冻结模型直读）、jevfire（tribute 致谢 Jev 的独立实现）、vllm#57250 的 DiffusionGemma demo 走的都是同一条路，社区 72 小时内多路线复现属实。

    2. **一致性是真实短板**：jev-demos（相同请求不同答案）与 phishing-bench（2.2% 标签翻转）独立观察到；SemIf 的 BF16 前缀复用路径也有 5–6/777 的 argmax 漂移。下游必须保留置信度缓冲带（官方 0.30–0.70 转人工）。

    3. **表征 > 模型**是四个仓库（02、05、08、09）的共同主线：输入状态表达、结构化控件表、WebMCP 工具化、确定性验证 + 升级契约，收益都是数量级；判断模型本身只贡献稳定的百毫秒决策。

    4. **能力边界一致**：长视野多步规划（迷宫）、纯阅读抽取、回溯类任务都不是判断模型的地盘；高频收敛的"单步裁判"才是。

    5. **时点判断**：所有仓库集中在 2026-09-15（Jev 发布）后 2–4 天内出现且引用同一批官方文档/发布物，印证文章"需求侧 agent 化 + 供给侧蒸馏基座 + 分发"三力合流的时机论。

    • OpenJev / SemIf 调研报告

  • 研究日期：2026-09-20
  • 仓库 commit：`ca3ba65`（浅克隆，路径 `planning/01-raw/repos/openjev`）
  • 读取文件：README.md、docs/RESULTS.md、pyproject.toml、benchmarks/verify_published.py（grep 定位，全文未读）、目录清单

    • 概述

    SemIf（原名 OpenJev）是一个独立开源研究项目，自称复现 TypeSafe 闭源服务 **Jev** 的"接口模式"（runtime-defined 语义决策），而非复现 Jev 的模型或训练。核心思路：多数 agent 决策是小型分类（路由、重试、证据是否支持 X），与其让模型生成文本再解析成 `if`，不如**一次前向传播直接读出各类型化选项的 logits 概率**——无答案生成、无 JSON 修复、无解码循环。支持浏览器 WebGPU demo 与 Python CLI 两种使用方式。

    实现原理

  • **基座模型：Qwen/Qwen3.5-4B**（冻结，BF16 原生推理；README 指定固定 revision `851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a`）。浏览器 demo 另含 Qwen3-0.6B、MiniCPM5-2B（GGUF 量化）。
  • **直接读出（direct）**：输入 = 非结构化 state + 运行时 criteria + 类型化选项描述；一次前向传播读取声明的选项字母 token 的原生 next-token logits，softmax 得到概率对。前一个 agent 已确认源码存在 `PROMPT_VERSION='direct-options-v1'` 与字母 token logits 的 softmax 归一化，与 README 描述一致。
  • **共享状态复用**：同一长 state prefill 一次后可在多个 criteria 间并行分支（serial prefix reuse / parallel suffixes），速度从 2.33 decisions/s 提升到 20.03 decisions/s（777 决策 333s→38.8s，RTX 3090）；代价是 BF16 复用路径下 777 个 argmax 中 5–6 个漂移（仓库如实标注）。
  • **对照实现**：Qwen3-Reranker-4B 作为原生 reranker 基线，在通用决策任务上明显弱于 direct logits（-0.115 ~ -0.188 balanced accuracy），仅检索排序时有用。
  • **MLX 后端**（macOS arm64）：直接评分、串行前缀复用、并行共享状态决策。

    • 评测与验证（文章声称 vs 仓库证据）

    文章声称仓库证据结论 冻结 Qwen3.5-4B，零训练/零采样只读README 明确"frozen Qwen3.5-4B""no answer token is sampled"；RESULTS.md 明确未做 RLCD/训练**可证实** 官方 102 个判断任务README/RESULTS.md 均写 "TypeSafe selected subset, 102 rows across 20 cases"；verify_published.py 引用键 `typesafe_public_102_equal_case_modal_agreement`**可证实**（但注意：这是"从公开产物可对齐的 102 行子集"，非 TypeSafe 报告的 711 行全量） SemIf 一致率 84.5%RESULTS.md：TypeSafe subset modal agreement = **0.845**，另报告 TV 距离 0.177（Jev 为 0.127）**可证实**（数值在仓库中，行级预测与原始结果在 `results/raw/`，但我未逐行核验数据文件本身） Jev 88.3%README/RESULTS.md："Published Jev … 0.883"，且明确声明"we did not run a live Jev endpoint"，该数字是从 TypeSafe 公开发表记录读取的**数值存在但不可独立证实**——仓库方自己强调样本小且经挑选、Jev 未经其复跑 复现 Jev 能力仓库明确"Not reproduced"：Jev 未公开架构、并行采样器、RLCD 训练**不可证实**；仓库立场是复现接口模式，差距 3.8 个百分点

    其他仓库内评测（direct Qwen3.5-4B）：自建 144 行 balanced accuracy 0.813；WANLI 256 行 0.637；judgment grid 0.806；鲁棒性扰动测试（选项反转/无关上下文等）显示选项顺序敏感仍是已知缺陷。

    评估结论

  • 实现与声称基本自洽：仓库代码、README、RESULTS 与 benchmark 脚本三方对齐，102 行 / 0.845 / 0.883 均在仓库文档中有明确出处，且附行级预测与原始结果文件，可信度较高。
  • 需注意口径：0.845 是"可从公开产物对齐的 102 行挑选子集"上的 modal agreement，不是全量；0.883 是 TypeSafe 自报数，仓库方未运行 Jev、未独立验证，且作者自己强调该对比"不确立 near-Jev 能力"（概率质量 TV 距离 0.177 vs 0.127 有明显差距）。
  • 技术亮点是 decision-native 直读 logits + 共享状态复用的系统路径（5.2× 快于生成式基线），而非模型能力超越 Jev。
  • 建议在引用时表述为："SemIf 用冻结 Qwen3.5-4B 以 direct logits 方式在 TypeSafe 公开 102 行子集上达到 0.845 一致率（Jev 自报 0.883，未经独立验证）"。

    • 02 — jev-behavior-study（Jev 行为研究：输入表征杠杆）

  • 研究日期：2026-09-20
  • 仓库：https://github.com/RINNECODER/jev-behavior-study，commit `e4a1d7e`（2026-09-17）

    • 概述

    对 Jev（`jev-1.13.0`）的大规模行为研究，含贪吃蛇（snake_demo）、城市 demo、日常推理、洗车/平地/斜视等多个基准报告，全部带 PROTOCOL.md（预注册式协议：候选配置先冻结再上 held-out 种子 9101–9116，事后不修改提示词、不换种子、不重试）与 QA.md。

    研究方法

  • **无辅助（unassisted）贪吃蛇**：12×12 棋盘、8 食目标、200 步上限；Jev 的最终选择原样执行，求解器只在游戏结束后用于打分，不进入任何模型请求（无路线答案、无安全标签、无动作掩码）。
  • 开发集 80 状态上测 8 种输入变体（原始/显式优先级/散文描述/ASCII 网格/头相对坐标/四步历史/绝对方向/双调用自审），预声明选择规则冻结决赛配置后再跑 16 局 held-out。
  • 调用量：主研究 4,515 次成功调用；开发+holdout 阶段另有 720 请求；全仓库基准汇总 `valid_calls=6,394`（另有 city/carwash/平地等报告），与文章"超过 1.1 万次调用"量级相符（合计口径）。

    • 关键发现（文章声称 vs 仓库实际证据）

    文章声称仓库证据判定 超过 1.1 万次调用单 snake 主研究 4,515 次、汇总 6,394 valid calls；各 demo 报告合计上万量级✅ 大体可证实（取决于合计口径） 输入改成清晰状态陈述 1/16 → 14/16unassisted REPORT：Original 1/16 vs Prose description **14/16**（Wilson 95%: 64.0–96.5%），冻结配置后 held-out，含配对比较✅ 可证实，且方法学严谨 路径事实写进输入达 16/16仓库明确区分：16/16 属于**早期 assisted 研究**（Jev 从代码算出的精确路线长度中选择）；unassisted 研究特意不提供任何路线信息⚠️ 数字存在但语境不同：那是"求解器喂答案"的上限实验，非同等条件对比 输入表征是决定性杠杆80 状态开发集：Prose 70/80 最短路 vs Original 55/80；head-relative 坐标单步 78/80 却在完整对局中撞车被预声明规则淘汰——表征好坏要看任务视野✅ 定性可证实

    补充发现：绝对方向 12/16、散文描述平均吃食 7.19 vs 3.06；API 中断按删失处理并如实披露；在贪吃蛇上确定性基线显著优于两个 Jev 配置。

    评估结论

    这是 9 个仓库中方法学最接近学术论文的一个（预注册、held-out、配对检验、删失处理）。它给文章最核心的论点——**"决定成败的是工程端的状态表达，而非模型间几个百分点"**——提供了最强的一手证据（1/16→14/16 = 87.5pp 的表征收益）。需修正的是：16/16 的满分来自喂入精确路线的 assisted 设置，不能作为"纯输入改写可达满分"的证据。

    • 一、概述

    jev-capability-atlas 是一个**独立、非官方、非 TypeSafe 赞助**的社区项目（自称作者 Zaious，文章引用的也是 `github.com/Zaious/jev-capability-atlas`），研究对象是 TypeSafe 的 "System One" 模型 **Jev**——一个只能输出类型化答案（Choice/Score/Noul，即选选项/打分/是非）、不做自由文本生成、训练目标为置信度校准（RLCD）的窄判断模型。

    项目定位明确：**不是排行榜**（明确引用 jev-benchmarks、thaiexam-jev-charts 而不重做），要回答的是"什么情况下它强、什么情况下它弱、为什么"。方法论纪律很突出：所有自测条目要求"真实 API 调用收据"（原始 log 存于 `suites/<slug>/runs/`），第三方数据须附一手来源；来源分级标签 🔬（自测）/ 📚（第三方跑分）/ 📖（官方文档）/ 💭（综合分析）。

    二、图谱构成

    核心判准轴（一条轴）

    > **正确答案能否完全从喂给模型的 `state` 里读出来？**（信号自足 vs 需要外部知识）

    信号自足（✅）信号不自足（⚠️） 分类任务（AG News 91%、Banking77 87%）纯知识回忆题（历史/常识考题，无背景段落） 引用支持度判读（claim+quote 给齐）需要与整个领域比较的评分（论文新颖性等） 反讽/讽刺检测（触发线索在给定文字内，含跨回合）类别本身重叠的分类（DAIR Emotion 48%，且置信度失准）

    覆盖维度

    **自测 suites（🔬，5 组，均有 runs/2026-09-19.json 收据）：**

    1. **citation-support-check**：引用支持度判读，5/5 全对（含改述低重叠、反转词高重叠两组对照），低信心（0.45）正确对应难例。

    2. **sarcasm-vs-sincere-praise**：反讽检测同句版 12/12、跨句版（计分题）10/10 全对；两个刻意模糊对照置信度分岔（0.19 vs 1.00）。原预测这是弱项，结果预测错了。

    3. **history-recall-context**：纯回忆 vs 给背景的三题对照（下文详述）——**仓库自称"最重要的一笔反例"**。

    4. **icu-alarm-classification**：PhysioNet 2015 ICU 心律警报 30 笔抽样，官方评分 0.271 输给"全放行"基线（0.39）；心搏停止/室速敏感度 0%。结论：state 里缺什么特征就补不回来，但错答置信度仅 0.14-0.51，无"自信答错"。

    5. **jev-latency-distribution**：30 次调用，中位 250ms、p95 299ms，唯一离群值是首次调用（连接冷启动），独立重现"赢在没有长尾"。

    **第三方跑分整理（📚，13 条，只翻译整理不重跑）：** ThaiExam（567 题，70.7%，111 模型中段班，速度/成本同组最强）；jev-benchmarks（AG News 91%/Banking77 87%/DAIR Emotion 48% 且平均置信 0.819、16% 题目正解概率为零）；jev-browser vs Playwright MCP（快 1.5x/省 1.6x，但纯文字抽取任务反而更慢更贵）；jev-ultrafast（Browser Use 官方，中位快 25%、协议调用少 91%）；TypeSafe 首发评测的独立批评（参考答案是两个前沿模型回答的平均值，非人工标注）；工具调用风险分级（91.7%，答错时置信度诚实下修，无"自信答错"）；DSPy 信心门槛弃权（ECE 0.0583，N=24 过小）；context 压缩辩论（256 笔工具结果 0 笔保留分超 0.3，因 state 只给长度占位符）；SQL ORDER BY 排序（简单任务六判准全过，困难任务 ECE 0.045→0.242，批次 40 行失效）；LlamaIndex 重排序（nDCG@5 +0.056/+0.086）；重排融合评测（单独重排去循环后 -0.028，RRF 融合 +0.064 稳定成立）；拆解判断代价（困难良性案例误判率 1.5%→37.2%，约 25 倍）；mastra 内容审核（9/9 挡恶意、0 误判）；湖北新闻分类（与 Flash Lite 约 85% 一致，分歧集中在需要人名外部知识的案例）；广告拆解 embedding 宣称查证（技术解释站不住）。

    另有 AGENTS.md（给 agent 的扫描判准）、browser-automation.md（浏览器自动化实施指南）、skill/jev-fit-check（打包成 Claude Skill）。

    机制定位（README 专节）

    三个否定句定义 Jev：不是状态机（真实语言理解，引 citation 两组对照为证）、不是瞎猜（confidence 是概率分布算出的统计量，RLCD 训练目标直指校准；但 DAIR Emotion 显示某些任务上置信度会往"显得更有把握"方向失准——最危险的失准方向）、不是推理模型（不做展开式多步推导）。关键区分：**类型保证 ≠ 正确性保证**——"不可能输出选项外的值"是数学保证，但选到哪个常常是错的。

    三、关键发现（文章声称 vs 仓库实际证据）

    声称 1："MMLU-Pro 上 Jev 83%，27B 开源模型 60%" —— **不可证实**

  • 全仓库 grep 无任何 MMLU 字样；capability-map.md 索引表和全部 translations 条目均未收录任何 MMLU-Pro 数据。
  • 文章把这句话与"Zaious 的能力图谱显示……0.90 高置信度错误事实"写在同一句里，读起来像是图谱的内容之一，**但 MMLU-Pro 83% vs 60% 这组数字在图谱中不存在**，未注明任何一手来源，属于文章自己的（未溯源）声称。可能出处是未收录的第三方跑分，无法从本仓库核实。

    • 声称 2："一旦输入缺少必要背景，Jev 会在 0.90 高置信度下给出错误事实" —— **可证实，且有完整收据**

    `suites/history-recall-context/runs/2026-09-19.json`（真实 API 响应，jev-latest）：

    案例题目有无背景选择置信度概率分布对错 A大清第二任皇帝无雍正**0.90**0.04 / 0.93 / 0.03✗（标准答案康熙） B大清第七任皇帝（冷门）无咸丰0.070.25 / 0.37 / 0.38✓（但接近三选一蒙对） C同 B + 背景段落有咸丰0.970.00 / 0.02 / **0.98**✓

    数字与文章声称精确吻合。但报告须如实转述仓库自己列出的限制：

  • **N=3**、单一标注者（出题兼判标准答案）、仅中文历史一个领域；
  • **案例 A 的标准答案本身有算法争议**（从 1644 顺治入关算第 2 任是康熙；从 1636 国号算第 2 任是顺治，三选项无严格正解），"错误事实"依赖于采用通俗算法这一判定；
  • 存在采样方差：案例 B 正式收据前的非存档同题跑分置信 0.08 选错（道光）。

    • 因此准确的表述是：**"存在一次高置信（0.90）答错的实测案例"可证实；"Jev 在缺背景时系统性给出错误事实"这一泛化结论，仅凭本仓库证据（N=3、一题争议标准答案）不成立。** 仓库自己也只主张定性结论："裸记忆存在真实风险，给背景可以修正。"

    声称 3（隐含）："信号自足任务表现好" —— 可证实但多为小样本自测

  • 自测三组（引用支持、反讽、历史-给背景）合计约 35 个计分案例，全对或近全对，有 API 收据；但样本小、题目由同一标注者设计，存在出题偏差风险。
  • 第三方大样本证据（jev-benchmarks 各 100 例、ThaiExam 567 题、工具调用 60 例、河北新闻 1000 笔抽样等）支持"干净分类任务强"的方向，但这些不是仓库自己重跑的。

    • 其他值得注意的发现（文章未提）

  • **置信度校准的失败面**：DAIR Emotion 平均置信 0.819、实际 48%、16% 题目正解概率恰为零——校准失准方向是"显得更有把握"，与 history-recall 的 0.90 错答构成同一类风险的两个独立证据（一个 🔬 一个 📚）。
  • **信号不自足的隐蔽形式**：context 压缩辩论中，state 只给占位符时 256 笔 0 笔保留分 >0.3——不是模型错，是调用方没给内容。与湖北新闻人名案例、ICU 特征缺失案例共同印证核心轴。
  • **成本立场**：订阅制下边际成本近零时插 Jev 只加延迟；Jev 划算的场景是原本每次判断单独付费调用大模型的场景。
  • **官方评测的可信度缺陷**：TypeSafe 首发评测参考答案是两个前沿模型回答的平均值，非人工标注（dev.to / Anthony Maio 批评）。

    • 四、评估结论："答案无法从输入推导时模型记忆同样靠不住"的证据强度

    **总体判定：方向有真实证据支撑，但证据规模小于文章给读者造成的印象。**

    1. **支持证据（仓库内）**：

    - history-recall-context 案例 A：0.90 置信答错常识史实题（🔬，唯一的高置信错误事实直接证据）；

    - 案例 B→C 同题对照：无背景置信 0.07 近打平 → 给背景 0.98 答对，证明给 context 可修正；

    - DAIR Emotion：类别重叠（需要超出给定文本的判别）时置信度系统性失准（📚，n=100）；

    - 湖北新闻：人名-地点关联（外部知识）案例是唯一分歧集中区（📚，生产规模）；

    - ICU 警报：state 缺判别所需特征时无法补救，虽然这次置信度诚实（0.14-0.51）。

    2. **削弱因素**：直接证据仅 1 个案例且标准答案本身有算法争议；整套自测 N=3、单领域、出题与判分同一人；"83% vs 60%"的 MMLU-Pro 数字无溯源，不能作为"记忆能力尚可"或"记忆靠不住"任何一方的依据；采样方差使单次收据不可复现（仓库自己承认）。

    3. **合理的最终表述**：仓库的证据足以支撑**定性**命题——"Jev 的裸记忆不可靠且可能以高置信出错，可靠能力来自 state 内文本的阅读理解；答案不在输入里时应先检索补齐 context，而不是指望模型记得"。文章把这句定性结论与一条无来源的 MMLU-Pro 数字捆绑引用，是超出仓库证据的强化表述；引用时应拆开：定性结论**可证实**（附上述限制），量化对比**不可证实**。

    4. **对 Jev 能力边界的图谱结论**（仓库自己的归纳，值得采信）：Jev 适合"大量、窄、平行、答案在给定文本内"的判断层；不适合纯知识回忆、类别模糊分类、需全域比较的评分、纯阅读理解（比 LLM 慢贵）、以及不可逆动作的无人监督决策（context 删除案例）。置信度数值"在某些任务上会往过度自信方向失准"，三段式信心门槛的阈值必须在自有数据上重新验证。

    04 — jevfire（本地 vLLM/WebGPU 并行分类解码）

  • 研究日期：2026-09-20
  • 仓库：https://github.com/kikoncuo/jevfire，commit `5df83b5`（2026-09-18）
  • 许可证：MIT；无再训练、无第二模型

    • 概述

    JEVfire 是对 Jev 的独立复现（作者自述受 harshatheg 的 Qwen-2.5-1B-RLCD demo 启发，"Named in tribute to JEV"）。核心思路：**用预训练模型现有的 language-model head 对经验证的单 token 标签打分**，把胜者映射到允许值，JSON 由应用代码拼装——即文章所说的"前向传播 + logits 归一化"路线，零训练。独立决策字段通过 vLLM 批量并行执行，共享 instruction/context 前缀以利用 prefix cache。

    技术架构

  • **CUDA/vLLM 后端**：实测模型 Qwen3.8-27B-FP8，RTX PRO 6000 Blackwell，vLLM 0.29.0；对 vLLM 的 patch 仅改 `sampling_params.py` 一个常量。
  • **浏览器后端**：WebLLM + WebGPU，模型为 Qwen3.5-0.8B 的 MLC 转换（Apache 2.0）。
  • **结构性保证**：schema 决定键和候选集，模型无法发明字段或集合外的值——但作者明确说明这是结构性保证而非事实正确性保证，模型仍可选错值。
  • 三个浏览器实验：Super Mario World 1-1（Qwen + 显式物理守卫的混合结果）、Slipstream 四车并驾、村庄 demo。

    • 性能数据（文章声称 vs 仓库实际证据）

    文章声称仓库证据判定 0.8B Qwen + WebGPU，马里奥每步 71.26msREADME 精确吻合：final-build run 71.26ms mean worker inference、511 accepted choices、40.12s 通关，设备为 Apple M4 Max（非文章暗示的消费级 GPU 场景，且"excludes model download and CPU forecasting"）✅ 可证实（有 Measurement receipt） 比 Jev API 178ms 快、无网络往返71ms 为 worker 推理延迟，非整个控制回路延迟；仓库未直接对比 Jev API⚠️ 部分可证实，对比系文章推断 本地方案确定性高README 未直接强调确定性，但单 token logits 打分机制上成立⚠️ 机制上成立，未做专门实测

    额外发现（文章未提）：CUDA 侧合成 28 字段任务上，JEVfire 比生成等价约束 JSON 快 **10.29×**（496.9ms vs 5113.1ms，fresh prefix；warm prefix 达 14.77×），基准含 260 请求初始实验 + 2622 请求调参（均为重复 fixture），原始数据发布在 `benchmarks/results/benchmark.json`。

    评估结论

    仓库工程质量高（CI、原始基准数据、诚实的局限性披露——如"这是 Qwen+物理守卫的混合结果"、"5 samples/cell 只是初步延迟估计"）。它最有力地验证了文章核心论点：**logits 提取式判断没有任何技术壁垒，且本地并行批量分类在延迟上可以大幅反超**。但需注意 71ms 的适用前提（0.8B 浏览器模型 + 单步决策 + 排除下载/预测开销）与 Jev 的云端 27B 级别能力并非同一量级的比较。

    05 — jev-ultrafast（Browser Use × TypeSafe 官方优化案例）

  • 研究日期：2026-09-20
  • 仓库：https://github.com/browser-use/jev-ultrafast，commit `1231850`（2026-09-18）

    • 概述

    Browser Use 官方的浏览器 agent 优化项目：**动态索引动作空间**。每步观察生成带标号的控件表（`[3] combobox Where from? · San Francisco`），Jev 在一次请求中同时选择操作（CLICK/TYPE_TEXT/SELECT/SCROLL/WAIT/DONE/BLOCKED）与目标元素（投机式：操作为 CLICK 时只有 click_target 能执行，两个决策一次网络往返）；只有 TYPE_TEXT 才由小 LLM（`inception/mercury-2.5`，关闭推理）生成文本。

    优化点分析

  • 一次快照一次浏览器调用，原子读取可见控件（名称/值/文本），**默认循环无截图**——Jev 消费结构化状态
  • 点击守卫：验证文档、表单值、目标与邻近上下文，拒绝被遮挡控件；动画不再触发重判
  • 组合框等待可见建议（上限 200ms）；隐藏标签页保持渲染；只发送可见文本
  • 模型输出永不变成 selector、坐标、shell 命令或可执行 JS

    • 性能数据（文章声称 vs 仓库实际证据）

    文章声称仓库证据判定 端到端 9.450s → 7.092s`docs/performance.md` matched comparison：6 次交替运行取中位，9.450s vs 7.092s，优化臂 3/3 全胜，任务时间降 25.0%✅ 可证实 交互调用 1092 → 101同上：median browser protocol calls 1,092 → 101；TypeSafe 请求 22 → 17✅ 可证实 Jev API 中位延迟 178ms录制报告：17 次 Jev 请求中位 178ms✅ 可证实 提速主要来自去除重复 a11y 树扫描README"Where the time went"：原循环每次 DOM 突变都作废决策、反复读 a11y 树、解析数百 DOM 节点；新快照一次浏览器调用读完✅ 可证实

    **仓库自己的诚实标注（文章未充分转述）**：三对样本太少，双侧 sign-test p=0.25，"不足以做强统计声明"；对比是受控小样本而非广泛的 agent 基准。

    评估结论

    这是"架构/表征改造是提速主因"的最佳官方实证：**两臂使用同样的 Jev（jev-1.13.0）和同样的 Mercury 文本模型**，收益全部来自快照与执行层改造（协议调用降 10 倍）。同时也说明 Jev 本身在链路里的贡献是稳定的百毫秒级决策，而非端到端提速的主要来源——支持文章"拿走架构，不带走模型"的结论。

    06 — jev-demos（迷宫寻路一致性实测）

  • 研究日期：2026-09-20
  • 仓库：https://github.com/Bud-ro/jev-demos，commit `37470f9`（2026-09-17）
  • 技术栈：Dart；`packages/jev_common`（API shim + 结果录制）、`packages/maze_lookahead`（空间推理/前瞻测试）

    • 概述

    作者（Bud-ro）用 TypeSafe System One 模型测迷宫求解，重点是**同时移动（simultaneous move making）**：一次请求问接下来的 N 步，任何回退/撞墙/踩到 G 后离开都判失败；并测试只执行前 M 步决策时的表现。

    一致性发现（文章声称 vs 仓库实际证据）

    文章声称仓库证据判定 重复相同请求无法稳定得到相同答案maze_lookahead README 原文："Identical requests do not always get identical answers"✅ 可证实 多次运行下迷宫求解率归零quick preset（10 个 5×5 到 2 个 100×100 迷宫、每请求 100 步问题）下 `#` 墙和 `█` 墙迷宫**均解出 0 个**✅ 可证实（原文用词为"solved zero mazes"，文章的"求解率归零"属实但语境是特定 preset） （文章引申）与本地 logits 方案确定性对比仓库未直接做本地 logits 对照；但引用了 vllm#57250 的 "Jev at home" DiffusionGemma structured-read demo：同一风格 5×5 迷宫无邻接提示、每步一次读取、20 步最优走到 G⚠️ 间接证据

    其他量化发现（文章未提）：计划呈"右→下→NONE"的直线倾向，下一步准确率仅 35–46%，从不回答 UP；**告知四邻格子内容可完全消除撞墙**，加上单步问题后 5×5 迷宫解出 6/10（4 个走最优路径），失败模式均为岔路口转错后在死胡同振荡。原始数据在 `results/`。

    评估结论

    一致性缺陷证据扎实且是仓库第一手观察；"求解率归零"成立但需注意是长视野（100 步计划）+ 大迷宫的 quick preset，小迷宫 + 邻接提示下成功率显著回升——与 02 号报告（jev-behavior-study）的"输入表征杠杆"结论互相印证。对生产系统的启示：**长视野多步空间规划不该交给判断模型**，且概率抖动要求下游必须设置置信度缓冲带（与官方 0.30–0.70 转人工的建议一致）。

    07 — jev-phishing-bench（钓鱼邮件判定基准：Jev vs LLM）

  • 研究日期：2026-09-20
  • 仓库：https://github.com/anisselbd/jev-phishing-bench，commit `1d56e8c`（2026-09-17）
  • 数据集：PhishNChips v5.2（2026-04），2000 封（1000 钓鱼 + 1000 合法，含 333 个跨域误报陷阱）

    • 概述

    公开可复现的安全决策基准：邮件 agent 是否该点击邮件里的链接。Jev（jev-1.13.0）与 Claude Haiku 4.5 在同样的 2000 封邮件、同一种子顺序、每封一次调用下对比准确率、召回、AUROC、校准（ECE/Brier）、延迟、成本与概率稳定性；所有比例带 95% Wilson 区间，准确率差用配对 McNemar 检验。

    关键数据（文章声称 vs 仓库实际证据）

    文章声称仓库证据判定 专用分类器 81.3% vs 零样本判断模型 62.6%**实际是 Claude Haiku 4.5（通用 LLM）81.3% vs Jev 62.6%**，并非"专用分类器"；81.3% 是通用对话模型在 balanced 系统提示词下的成绩❌ **文章失真**：对比对象被错标。但"81.3% vs 62.6%"两个数字本身真实 结论：标签固定+样本充足时专用分类器更有优势仓库结论更微妙：Jev 的最佳单信号（sig_free_hosting≥0.70）89.4%，**低于两行正则规则的 91.8%**（p=0.003）；但对 Jev 五信号做逻辑回归达 95.0%，统计上追平 Haiku 信号的回归（95.0% vs 93.2%，p=0.063）⚠️ 文章结论方向对（零样本判断不够），但论据错位

    其他重要发现（文章未提）：

  • Jev 钓鱼召回仅 43.2%（Haiku 76.4%），AUROC 0.689 vs 0.837，ECE 0.154 vs 0.097
  • **稳定性**：两次通过之间 Jev 2.2% 标签翻转（mean abs diff 0.017），200 封 12 小时后 1.0% 翻转；Haiku 300 封 0.7% 翻转
  • Jev 胜在便宜快：$0.038 vs $0.462 /千封（约 12×），p50 239ms vs 687ms；信号分解更是便宜约 27×、快 5×
  • 方法学严谨（公开数据集后置于模型训练截止、程序化验证、非 AI 基线对照、A/B split）

    • 评估结论

    这是 9 个仓库中方法学最严谨的一个，且**直接证伪了文章的转述**：所谓"专用分类器 81.3%"实为通用 LLM。仓库的真实教训比文章更尖锐：零样本判断模型在安全决策上既输给通用 LLM 也输给两行正则；它的价值只在"便宜地提供可回归的中间信号"。使用本文数据时应以仓库为准。

    08 — WindTunnel（WebMCP 表征基准：感知/判断解耦）

  • 研究日期：2026-09-20
  • 仓库：https://github.com/nekuda-ai/WindTunnel，commit `5ca8644`（2026-09-18）
  • 许可证：Apache-2.0；基于 W3C WebMCP 规范（webmachinelearning/webmcp）

    • 概述

    基准仓库，比较浏览器 agent 操作网站的三/四种接口：截图（computer use）、页面结构（DOM/a11y 树）、代码执行（Playwright）、**WebMCP**（网站直接暴露 `add_to_cart(id)`、`book_slot(time)` 等工具调用）。规模：21 配置 × 49 任务 × 8 站点 × 3 次 = 3,087 attempt 行、1,029 多数裁决，600s/次上限（canonical board v1.2，2026-09-18）。

    架构分析

    WebMCP 是"网站自己提供语义化动作"的表征方案——agent 不再解析像素或 DOM，而是调用站点声明的能力。各 method（`arms/`）+ 模型组合成 21 个配置；多数裁决 + 负控站点（不该行动时只能回答）+ outcome probe（只读探查真实状态判定成败）+ perturbation（改名按钮/弹窗等对抗扰动，单独报告）。

    基准数据（文章声称 vs 仓库实际证据）

    文章声称仓库证据判定 同一模型原始 DOM 表 25/49（中位 5.4s），换 WebMCP 后 49/49（中位 3.2s）README："New: Jev + Mercury 2.5 solves **49/49 tasks with WebMCP** and **25/49 with ultrafast DOM controls**"；WebMCP 对该组合 1.7× 更快⚠️ 完成率数字 ✅ 可证实；5.4s/3.2s 中位耗时未在 README 出现（或在 results/ 明细中），1.7× 与之方向一致 表征改造拉开 44 个百分点，远超模型间 3.8 个百分点49-25=24 个百分点（25/49≈51%→100%），文章的"44 个百分点"系错误换算❌ **数字有误**（实际 +24pp），但"表征差距 >> 模型差距"的定性结论成立 表征改造是头号功臣属工程推断、无消融实验仓库未提供"同表征下换判断模型"的隔离消融；且 9 个 WebMCP 配置 + GPT-6 Astra 代码执行均满分 49/49，"任务解出率"上 WebMCP 与最强截图方案打平，**区分度来自成本与时间**（3–47× 便宜、2.5–7.5× 快）✅ 消融缺口属实；文章的"44pp 成功率跃升"表述夸大了

    另注意：GPT-6 Astra 代码执行总成本 $35.53 vs 原生 WebMCP $3.33（10.7×），中位时间 16.4s vs 6.3s。

    评估结论

    WindTunnel 证实"感知/判断解耦 + 表征改造"能带来数量级的成本/时间收益，但文章两处转述失真（44pp 应为约 24pp；成功率上 WebMCP 并未独占满分）。更准确的版本是：**在满分俱乐部内部，接口表征决定的是成本与速度，而非成功率**。文章提醒的消融缺口确实存在——"表征 vs 判断模型谁更重要"尚无隔离实验。

    09 — jev-browser（Jev 驱动的浏览器 MCP 服务器）

  • 研究日期：2026-09-20
  • 仓库：https://github.com/MahmoudAdelbghany/jev-browser，commit `20c27dd`（2026-09-17）
  • 技术栈：Node ≥20 + Playwright；Jev `jev-1.13.0`；驱动模型 `auto/best-coding` via Claude Code 2.1.245

    • 概述

    把 Jev 包装成浏览器 MCP 服务器给 LLM agent 用：一次 `page.evaluate` 快照（2–25ms）→ 本地按目标词重叠排序的紧凑候选列表 → **一次 Jev 并行调用**（~300ms，零 LLM token）同时决定 action、element、key、字段↔文本绑定、上步验证（prev_ok）、完成检测（goal_achieved）→ CDP 执行 → 确定性状态 diff 验证；低置信/卡死/循环时升级给 LLM（escalation contract）。

    基准数据（文章声称 vs 仓库实际证据）

    文章声称仓库证据（RESULTS.md，2026-09-17）判定 单任务中位 1.8sjev-only 栈 12 任务（jev-only n=3 共 33 轮）avg wall/task p50 **1.8s**✅ 可证实 成本约 $0.0005/任务$0.017/33 轮 ≈ $0.0005✅ 可证实 完成率 97%32/33 = 97%✅ 可证实 （文章未强调）与 LLM agent 对比vs Claude+Playwright MCP：~10× 快、~100× 便宜、同套件 97% vs 100%；同驱动下 claude-jev 比 claude-playwright 快 1.5×、省 1.6×、同为 12/12✅ 补充

    设计细节：类型化 ref 使 Jev 无法幻觉出不存在的动作（非法组合纠正性重问一次）；确定性验证覆盖 Jev 的弱信号；置信度分层策略（可逆动作 0.3、其余 0.5）把成功率从 94% 提到 97%。

    局限（仓库自述）

  • Claude 两栈 n=1（成本预算），比例仅方向性参考；本地确定性任务为主，仅 2 个 Wikipedia 实网任务
  • Jev 单独会败于回溯类任务（t03 需导航返回），靠升级路径恢复——这是设计内行为
  • 纯阅读抽取任务（l02）Jev 反而更慢更贵：大页面状态推给 Jev 的输入成本高于 LLM 自己读快照 → "读和答"归 LLM，"在页面上行动"归 Jev

    • 评估结论

    三个数字全部在仓库中可证实，且仓库提供了复现命令（`node bench/compare.mjs ...`）与程序化验证（服务端随机 8 位码防 LLM 裁判偏置），方法学可信。它给出文章结论最干净的工程佐证：**判断模型 + 确定性验证 + 升级契约**的组合可以在窄域任务上以 1/100 成本逼近 LLM agent，同时明确划出了判断模型的能力边界（回溯、纯阅读）。

    10 — Kev 与 Bespoke Nimble：训练方法与数据集（自研微调参考）

  • 研究日期：2026-09-20
  • 信息源：微信公众号文章《JEV：一个只会说「选A、打3分、是」的AI模型爆了，48小时炸出14个项目》（存档 `01-raw/wx-jev-kev-nimble-202609.md`）+ 两仓库一手核验
  • 仓库：nimble `35fe1f4`（2026-09-19）、kev `20fa626`（2026-09-19）
  • **定位：本报告侧重"我们以后做自己的微调决策模型时能直接抄什么"**

    • 一、两条微调路线速览

    Bespoke NimbleKev (Jared Palmer) 基座Qwen3.5-9BQwen2.5/Qwen3 0.5B–8B（推荐 4B） 方法LoRA（rank 16）+ 答案 token 交叉熵LoRA（r=16）+ 从零训练的 pointer readout head（0.46M） 可训参数LoRA 适配器9.3M（占 backbone 1.9%） 训练数据2,676 条对比对（10 领域）10–13 个公开源 ×1,000 条 + 2×448 条程序化策略对（decision-v4/v6 suite） 关键超参lr 5e-5、effective batch 8、1 epoch、BF16、seed 17、2,048 token 限长lr **5e-5**（最大单项改进）、2 epochs、batch 4×accum 2、bf16 autocast 成本调参 L40S、终训 H100kev-4b 单 H100 ~40 分钟；0.5B 试验 $0.15–0.30；M5 笔记本 0.06 度电 成绩324 held-out 90.12%（Jev 93.21%，基座 66.36%，Qwen3.8-27B 84.88%）OOD：kev-4b 0.79 / kev-8b 0.80（Jev 0.86） 许可Apache 2.0（数据/权重/配方/推理全公开）开源 + HF 集合

    二、Nimble：contrastive data curation（最值得抄的数据方法）

    **核心思想**：没有 teacher 概率可蒸馏，就构造**最小对比对（minimal pairs）**——两条样本几乎完全相同，只改一个关键事实使正确答案翻转，标签是硬的（对/错）。模型被迫学会"哪条证据才应该改变决策"，从而把 logits 校准到可用。

  • 文中例子：规则"只有 Mira 可授权账户 42 退款"；对比对只把签名人 Mira→Noah，答案 true→false，其余文本（问题、政策）逐字相同
  • **无需人工标注概率、无需蒸馏**；训练目标是 allowed candidate logits 上的交叉熵（直接学类型化决策）
  • 仓库明确："只拿 Jev 评估，不用 Jev 输出"；保存的 Jev 概率仅留作未来 soft-target 蒸馏的选项
  • 数据集：`data/train.jsonl` 2,826 条（发布模型用 2,676）/ `data/eval.jsonl` 324 条（仅终评）。覆盖 Commerce、Education、Media、Public Services、Supply Chain、Travel、Workplace 等 10 领域
  • 题型分布（训练/holdout）：Choice 1,244/260、Noul（布尔）500/0、Score 932/64
  • **标签全部是合成且由模型自查、无人复核**——同模型多次调用可能犯同样的错，作者自己承认此局限

    • 三、Kev：架构隔离与"学习率保知识"

  • **单次 prefill 多问题**：state 编码一次，多个 question 经 block-causal mask 并行独立推理（问题间互相不可见，隔离性验证到 4e-6 精度）；pointer head 对每个问题的 decide token × option token 打分后 softmax
  • **训练/推理同一 renderer**：线上请求与训练数据走同一格式管线，推理不会遇到训练没见过的格式
  • **学习率是保住基座能力的关键**：默认 2e-4 会把基座知识"训没"，降到 **5e-5** 保住大部分——这类微调不是学新知识，而是教模型"用"已有能力做决策（低漂移旋钮 lora_targets/head_lr/weight_decay 均不敌 lr 5e-5）
  • 数据来源：公开数据集转 TypeSafe 形状（Banking77、AG News、MNLI、BoolQ、SST-5、Yelp 等）+ 程序化 policy pairs，冻结为带校验和的 suite（`evals/`）
  • 可选数据增强：`--p_none_pair`（部分 Choice 记录附加 none-of-the-above 最小对）；`--option_isolation`（选项隔离子分支，置换不变但 4B 上损精度）
  • 严谨性：每个 trial 记录 git commit、suite hash、代码 hash，不一致拒绝运行；训练 TF32/bf16、评估 fp32-exact（TF32 本身就会移动概率 ~1e-3）

    • 四、两文互相印证的结论

    1. **无需蒸馏、无需秘密配方**：LoRA + 答案 token 交叉熵 + 硬标签即可逼近 Jev（差 ~3pp）

    2. **lr 5e-5 是两个项目共同的甜点**（Kev 的最大单项发现；Nimble 终选配方同为 5e-5）

    3. 数据质量杠杆在**对比结构**（翻转关键事实）而非数据量——2,676 条就够把 9B 从 66% 拉到 90%

    五、局限（做自研模型时要避的坑）

  • Nimble 测试仅 324 条/162 对/6 领域，作者自认"换测试可能远不如 Jev"；单一 held-out 高分易掩盖线上风险，应补**校准曲线与分布外测试**（评论区共识）
  • Kev OOD 差 Jev 6–7pp，短板集中在知识题（MMLU 0.69–0.75 vs 0.90）和日期算术——**基座缺的知识微调补不回来**
  • 合成标签自查有系统性盲区；Nimble holdout 的 Noul=0（布尔判断无 held-out 覆盖）

    • 六、对我们的可执行参考（GB10 自研微调）

    1. **数据**：优先复刻 contrastive data curation——按业务写策略/规则文本，程序化生成最小对比对（改一个字段翻转标签），题型覆盖 Choice/Noul/Score 三类

    2. **配方起点**：LoRA r=16、lr 5e-5、1–2 epochs、BF16、答案 token 交叉熵；单卡即可（kev-4b 一张 H100 40 分钟量级，GB10 上 4B 级基座可试）

    3. **基座**：知识类任务别指望微调补；选带足够 MMLU 的基座（4B–9B 档），体积优先则 Kev 路线（readout head + block-causal 多问题）

    4. **评测**：冻结 held-out suite + 校准曲线（ECE/可靠性图）+ OOD 集，别只看单一准确率

    5. 参考实现：`repos/nimble/data/`（现成 2,826+324 条样例数据）、`repos/kev/kev/{contrastive,data,train}.py`（对比对生成与训练循环）
